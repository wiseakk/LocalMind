# ГОТОВАЯ МИССИЯ ДЛЯ DEV CREW

## Миссия

Развить СУЩЕСТВУЮЩИЙ проект LocalMind MVP 0.1 из этого репозитория до воспроизводимого автономного локального голосового ИИ-ассистента с безопасным контролем оборудования. Не переписывать всё с нуля. Пользователь — школьник, который лично должен понимать и защищать проект на научно-практической конференции. Время — 10–14 дней, но first working build нужен немедленно.

## Процесс DevCrew

Используй существующую команду/цепочку Architect → Builder → Tester → Visual QA → Reviewer → Security с изолированными Git worktrees, QA/repair циклами и понятными диффами. Не сливай сломанное в main. После каждой миссии оставляй работающую версию и git commit. Если задача длинная — раздели на независимые маленькие PR/ветки. Каждая фича должна иметь тест или повторяемый ручной сценарий проверки. Никаких заявлений об успешном тесте без реального лога запуска.

## Что уже есть

FastAPI (`localmind/server.py`), Ollama tool calling + быстрые правила (`localmind/agent.py`), Home Assistant через разрешённый шлюз (`localmind/devices.py`), демо-лампа, `static/index.html`, README, pytest, .env.example.

## Приоритет задач

**P0 — сделай первым:**
1. Подними и проверь текущий MVP на Windows 10/11 + Ollama `qwen3:4b`; все текущие тесты должны проходить.
2. Улучши архитектуру аудио без внешнего облака: локальный STT (faster-whisper), локальный TTS (Piper), push-to-talk сначала; индикаторы состояния и разделённые метрики latency STT/LLM/TTS.
3. Добавь надёжный протокол клиент↔сервер: явное сопряжение устройств, авторизация, ограничения сети, отдельный низкоуровневый satellite API; не публикуй Ollama и сервер в интернет.
4. Введи детализированный журнал маршрутизации: request id, timestamps, выбранный fast path, инструмент, результат, задержка. Не логируй токены/записи по умолчанию.
5. Сделай реальные интеграционные тесты на Home Assistant (реальное устройство только при явном включении и конфигурации), и постоянные unit-тесты на фейковом шлюзе.

**P1 — только после стабильного P0:**
6. Аппаратный/отдельный LAN-клиент на ESP32-S3 или второй ноутбук: запись голоса, отправка, воспроизведение ответа. Никаких работ с сетевым 220 В.
7. Установка: скрипты Windows и Linux, проверка GPU/CPU и выбранной модели, понятные сообщения об ошибках.
8. Бенчмарк: reproducible CSV, p50/p95 latency и success rate на 30–50 запросах; сравни правила и LLM; офлайн-тест.
9. Обнови интерфейс (автоматическое обнаружение состояния, таймлайн запросов, статус устройств, режим DEMO/REAL, загрузка CPU/GPU при наличии).

## Жёсткие требования

- Никаких shell/exec/eval, произвольного файлового доступа или внешних URL по желанию модели.
- Инструменты строго allowlist, валидировать аргументы на стороне сервера; подтвердить опасные действия, если позже появятся.
- Демо и реальные устройства нельзя путать на UI. При отсутствии настоящего прибора показывать честную симуляцию.
- Никакой отправки голоса или переписки в облачные LLM/STT/TTS без явного решения пользователя.
- Secrets only in `.env` или OS key store, не в Git, не в логах.
- Для голоса на телефоне не полагаться на HTTP getUserMedia в LAN: нужен безопасный контекст/отдельное нативное приложение/спутник.
- При несовместимых версиях Ollama/Piper/ESPHome фиксируй проверенные версии и реальные ссылки на документацию.
- Для каждого файла, который изменяешь, добавь 1–3 понятных предложения: что делает и почему так. Для нетривиальных функций — обучающее объяснение строк/вызовов.
- Не пытайся за одну миссию разрабатывать собственную фундаментальную LLM, универсальный драйвер всех IoT-устройств или промышленный 220-вольтовый девайс.

## Definition of done

В корне должны быть: рабочий исходный код, тесты, `README.md`, `.env.example`, скрипт проверки конфигурации, `docs/ARCHITECTURE.md`, `docs/HOW_IT_WORKS.md` (понятные объяснения для 10 класса), `docs/DEFENSE_QA.md` (не менее 25 вопросов), `docs/EXPERIMENTS.md` и пример результатов замеров с отметкой «демонстрационные» или «фактические».

В итоговом отчёте ДЛЯ ПОЛЬЗОВАТЕЛЯ напиши:
1. Что реально работает, что эмулируется, что не работает.
2. Какие команды на Windows запустить по порядку.
3. Что сделано лично архитектурно и чем отличаются существующие библиотеки.
4. Логи тестов, необработанные проблемы, риски.
5. Пять неожиданных вопросов жюри и правильные ответы на уровне 10 класса.

**ПЕРВАЯ КОНКРЕТНАЯ МИССИЯ:** запусти проект, исправь обнаруженные дефекты, реализуй полный локальный push-to-talk pipeline STT → агент → Piper TTS → звук обратно в клиент. Сначала unit-tests и рабочий end-to-end на localhost, только потом переходи к спутнику.
