# LocalMind — вопросы жюри и краткие понятные ответы

**Главная идея:** тяжёлые вычисления выполняются на ПК пользователя, отдельный терминал в комнате отвечает за звук, Home Assistant обеспечивает стандартный интерфейс с совместимыми устройствами.

1. **Чем вы лучше Алисы?** Мы не доказали, что лучше во всём. Наш акцент — локальность обработки, контроль вызовов инструментов и прозрачный журнал. Сравниваем в своей тестовой методике, не обещаем невозможное.
2. **Почему колонка не запускает LLM сама?** Микроконтроллеру не хватает RAM/вычислительных ресурсов для выбранной модели с приемлемой скоростью. ПК повторно использует имеющийся GPU.
3. **Что такое LLM?** Большая языковая модель, которая предсказывает последовательность токенов и формирует ответы. Сама по себе она не управляет лампой.
4. **Как лампа включается по команде?** STT → редактируемый текст → явная отправка пользователем → серверный маршрутизатор → строго ограниченная функция `set_light` → Home Assistant REST API → драйвер устройства.
5. **Зачем правила, если есть LLM?** Чтобы для ясных команд обойти медленную/недетерминированную модель, ускорить ответ и снизить количество ошибок.
6. **Как защитились от опасных команд?** Нет функции «выполнить произвольную команду». Сервер принимает только допустимые функции и параметры, сверяет список разрешённых устройств/приложений.
7. **Что такое tool calling и используете ли вы его?** Это структурированный запрос модели к функции. В текущей безопасной версии Ollama формирует только текст, а действия выбирает детерминированный серверный маршрутизатор; так модель не может подменить действие или цель.
8. **Что такое Matter?** Открытый стандарт совместимости для поддерживаемых устройств умного дома; не то же самое, что Wi-Fi, Thread или Zigbee.
9. **Зачем Home Assistant?** Унифицирует интеграции. Наш сервер знает `entity_id` устройства и вызывает действие; Home Assistant взаимодействует с конкретной интеграцией.
10. **Почему нельзя подключить любую китайскую розетку?** Нужна поддерживаемая интеграция или стандарт. Некоторые модели требуют облачного API.
11. **Что, если отключить интернет?** При заранее загруженных моделях текстовый LLM и локальное распознавание речи работают без интернета. Однако облачные интеграции могут перестать работать, а голос браузера не обязательно офлайн.
12. **Что, если выключить ПК?** Тяжёлые вычисления недоступны. В прототипе это честное ограничение.
13. **Почему используете чужую LLM?** В исследовательском проекте задача не создавать фундаментальную модель с нуля, а разработать управляемую систему и измерить её свойства.
14. **Какая научно-техническая гипотеза?** Гибрид правил и LLM может ускорить выполнение однозначных команд без ухудшения их корректности относительно вызова LLM для каждого запроса. Это проверяется экспериментом, а не принимается на веру.
15. **Как измеряете успешность?** Список тестовых команд и заранее заданный ожидаемый исход; фиксируем реальный результат и время, считаем долю успешных.
16. **Что сделал автор?** Архитектура, безопасный шлюз, интеграция, тесты, измерения, документация, демонстрация. Использование ИИ-кодогенерации нужно честно указывать в соответствии с правилами конкурса.
17. **Что ещё не реализовано?** Аппаратный терминал, безопасное сопряжение и локальный TTS должны быть помечены как перспективные, пока не готовы. Не выдавать демо-лампу за реальную.
18. **Почему сервер недоступен из локальной сети?** В прототипе ещё нет безопасного сопряжения и TLS. Поэтому сервер жёстко привязан к `127.0.0.1` и отклоняет не-loopback клиентов; LAN появится только вместе с защищённым каналом.
19. **Почему недостаточно одной хорошей демонстрации?** Научно-практический проект требует повторяемого тестирования: замеры, ограничения, подтверждение результатов.
20. **Где ваше собственное инженерное решение?** Гибридная маршрутизация, граница доверия между LLM и управлением устройствами, реализованный шлюз и методика измерений.

## Распределение защиты

**Технарь:** архитектура, локальный сервер, LLM/STT, вызов инструментов, алгоритм, измерения, трудности, вопросы про безопасность.

**Соавтор:** проблема, целевая аудитория, сценарии, сравнение с существующими решениями, тест-план, интерфейс, ограничения, выводы. Не просто читает слайды, а может рассказать шаги команды своими словами.

Договоритесь, кто за какую часть действительно отвечал. Каждому стоит быть готовым к 3–5 базовым техническим вопросам.
