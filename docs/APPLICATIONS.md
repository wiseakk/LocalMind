# Проверенный каталог приложений Windows

`localmind/apps.py` обнаруживает ярлыки в пользовательском и общем меню «Пуск»,
на пользовательском и общем рабочем столе, а также регистрации **App Paths**
HKCU/HKLM в 32- и 64-битном представлениях реестра. Системные папки получаются
через `SHGetKnownFolderPath`; PATH для поиска программ не используется.
Приложения не устанавливаются, реестр и ярлыки не изменяются.

## Как разрешить запуск

Открой настройки → приложения → обнови каталог. Проверь отображаемый абсолютный
путь и разреши конкретное приложение. Разрешение действует только до перезапуска
сервера. Затем отправь точную команду, например «Открой Obsidian».
Обнаружение само по себе разрешением не является. Два приложения с одинаковым
именем требуют выбора конкретной записи в интерфейсе; неоднозначная текстовая
команда не запускает ни одно из них. Встроенные калькулятор и блокнот сохраняют
отдельный, ограниченный Windows System32 шлюз.

Список поддерживаемых имён исполняемых файлов находится в
`SUPPORTED_GUI_EXECUTABLES`. Он включает Codex desktop, Obsidian, Discord,
Visual Studio Code, основные браузеры, Office, VLC, OBS, 7-Zip и ряд редакторов.
Имя появляется в каталоге только при фактическом обнаружении безопасной цели.
Произвольные утилиты не становятся возможностью запуска лишь потому, что нашли
их ярлык. Расширение списка требует проверки кода.

## Что проверяет шлюз

1. Ярлык читается через нативный COM `IShellLinkW`/`IPersistFile`; метод `Resolve`
   не вызывается, Windows не ищет замену в сети. Из ярлыка берутся только путь и
   аргументы. Рабочая папка, значок и произвольные параметры игнорируются.
2. Разрешён только существующий абсолютный локальный `.exe` с заголовками MZ/PE
   и подсистемой Windows GUI (консольная CUI отклоняется).
   Запрещены UNC/URL/device-пути, альтернативные потоки, оболочки, интерпретаторы,
   установщики, удаление программ и **любые непустые аргументы** ярлыка.
3. SHA-256 источника, разрешённого абсолютного пути и содержимого exe образуют
   отпечаток. API разрешений принимает только id обнаруженной записи и текущий
   отпечаток из интерфейса, а не произвольный путь.
4. Перед каждым запуском повторно читаются ярлык/регистрация и exe. Изменение
   отзываeт разрешение. Даже легальное обновление приложения требует нового
   выбора. Во время финальной проверки и `CreateProcess` Windows-дескриптор exe
   запрещает параллельную запись/удаление файла.
5. Создаётся только один процесс через `subprocess.Popen([absolute_exe],
   shell=False)`. Аргументы модели, текст пользователя и содержимое ярлыка не
   передаются в shell. Рабочая папка — проверенная папка exe.

Ответ «создан процесс» не доказывает, что окно появилось или приложение готово.
Автоматическое закрытие остаётся запрещено: шлюз не выбирает чужие окна и не
рискует несохранённым текстом блокнота.

## Ограничения

Поддерживаются обычные локальные GUI exe. Ярлыки MSIX/UWP, ссылки на сайты,
Codex CLI, аргументы Electron updater (частый вариант установки Discord),
команды с флагами и нестандартные запускатели намеренно не разрешаются.
Discord обнаружится, если существует поддерживаемая регистрация прямого
`Discord.exe` без аргументов. Отсутствие программы в каталоге не доказывает,
что она не установлена: её способ запуска может быть неподдерживаемым.

Каталог ограничен 5000 просмотренными файлами, 6 уровнями папок, 256 источниками,
20 секундами между источниками и 512 МиБ на проверяемый exe. Повторное сканирование
выполняется одним потоком, с паузой минимум 2 секунды после завершения. Каталог читает только
метаданные установки и исполняемые файлы; документы/история пользователя не
сканируются. Отпечаток обнаруживает изменение, но не заменяет проверку
происхождения установленного ПО самим пользователем.

## Реальная проверка этого checkout

На Windows 28.10.2026 нативный COM прочитал реальный установленный ярлык без
запуска цели. После ограничения GUI-каталога read-only сканирование обнаружило
17 записей за 1,35 с: среди них Obsidian, VLC, OBS, 7-Zip, Office и PyCharm.
Все 17 первоначально запрещены. Codex, VS Code и Discord в проверенном каталоге
не обнаружены. Это проверка обнаружения, **не** проверка запуска 17 приложений.

`tests/test_apps.py`: 26 тестов проверяют отказ без разрешения, устаревший picker,
подмену exe/ярлыка, исчезновение файла, ошибки запуска, неоднозначные имена,
стабильность id, отсутствие ложных Codex-алиасов, запрет CLI/скриптов/аргументов,
отзыв разрешений при обновлении и реальное чтение Windows COM. `Popen` в тестах
запуска подменён; запись/удаление пользовательских файлов не выполнялись.

Для ручной проверки выбери пять доступных безопасных GUI приложений в picker,
разреши их и последовательно отправь команды. Сверь появление каждого окна с
техническим результатом. Закрой окна вручную, сохранив открытые документы.
Затем перезапусти сервер и проверь, что разрешения сброшены. При изменении
ярлыка/обновлении exe повторное разрешение обязательно.

## Повторные запросы и состояние приложения (overhaul)

Перед запуском `windows_state.py` читает список процессов Windows через
`WTSEnumerateProcessesW`. Имя exe используется только для выбора кандидатов:
совпадение подтверждается полным каноническим путём образа, SID пользователя
и текущей сессией. После открытия процесса SID и сессия проверяются повторно,
чтобы не доверять устаревшему PID из списка. Время создания FILETIME сохраняется
в снимке; открытые дескрипторы удерживаются во время `EnumWindows`, после которого
проверяется, что процесс не завершился. Права ограничены чтением сведений,
окна не активируются и процессы не завершаются.

Состояния: `visible_window`, `background`, `absent`, `unavailable`.
Видимое окно подтверждается только для проверенного процесса, не для другого exe
с тем же именем. Неопределённость или отказ доступа отменяет повторный запуск,
а не считается отсутствием приложения. Ярлыки на брокеры/UWP и окна отдельных
дочерних exe не позволяют доказать состояние главного окна и остаются ограничением.

Общий координатор держит блокировку от проверки состояния до создания процесса.
Таким образом разные request_id также не порождают параллельных запусков одного
образа. Уже работающий процесс подавляет запуск независимо от наличия окна.
Собственный `Popen` удерживается как дескриптор процесса, без предположения, что
числовой PID всё ещё принадлежит ему. При завершении запускателя сохраняется
15-секундный интервал передачи управления; ответ `launch_pending` не утверждает,
что окно появилось. После интервала повторный запуск возможен только при новой
успешной проверке отсутствия процесса. Дескрипторы и блокировки ограничены.

Проверка текущего checkout: 21 тест в `tests/test_windows_state.py` проверяет
сериализацию 24 конкурентных запросов, запуск в фоне/с окном, задержку,
завершение и ошибки, разные образы с одинаковым именем, смену SID/сессии между
перечислением и открытием, отказ доступа и выход во время перечисления окон.
Большинство границ Windows подменены. Отдельные read-only тесты на этой Windows
подтвердили текущий PID интерпретатора и FILETIME, а также отсутствие уникального
тестового exe. `EnumWindows` в sandbox возвращает 0, last-error 0: реальное
различение видимого/фонового Steam и запуск Steam здесь не подтверждены.
