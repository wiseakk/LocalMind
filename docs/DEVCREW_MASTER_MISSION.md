# LocalMind 1.0 — мастер-ТЗ для DevCrew (27 октября 2026)

## 0. Что разрабатываем

LocalMind — автономный **голосовой ассистент с личным ПК-сервером**. На ПК Windows 10/11 работают Ollama + LLM, STT, TTS, системный шлюз управления; отдельный клиент/колонка в дальнейшем подключается по домашней сети. Проект для научно-практической конференции «Инженеры будущего». Пользователь — ученик 10 класса, один из двух авторов, который должен понимать код на защите. Потребительский приоритет: приятно пользоваться ежедневно. Исследовательский приоритет: доказать точность, производительность и безопасность экспериментами.

**Текущий baseline**: ранее работал на реальном Windows 10 с RTX 4070 (Ollama qwen3:4b: GPU), faster-whisper с исправлением несовместимости PyAV, чат, открытие калькулятора/блокнота, демо-лампа. Пользователь прислал реальные логи `POST /api/transcribe 200`, `POST /api/chat 200`. Текущие 9 unit/mock тестов проходят в эталонной среде. Это не означает, что STT качественный или все инструменты в новой версии будут работать. Каталог приложений ограничен двумя именами. В `requirements-voice.txt` закреплена `av==18.1.0`, потому что установленный PyAV 19 не поддерживал `metadata_errors`.

## 1. Баги, подтверждённые пользователем

- «пельмени» распознаются неправильно; слова/сочетания для коротких команд часто портятся.
- «Открой Codex» → недоступно из-за захардкоженных `calculator` / `notepad`; пользователю нужно запускать реальные установленные приложения.
- LLM раньше ошибочно отказывалась рассказывать RSA, пельмени, ссылаясь на отсутствие интернета; сейчас частично скорректировано, нужна регрессия.
- Строки «Запустя калькулятор», «сварить в пельмене» требуют редактируемой расшифровки и улучшенной обработки речи.
- Функции закрытия ограничены и небезопасно убивать весь процесс `CalculatorApp.exe` через taskkill; заменить на безопасное адресное закрытие либо отказаться от закрытия с объяснением.

## 2. Требования продукта (по приоритетам)

### M0 — Аудит текущего репозитория, сохранение baseline

1. Запусти `python -m pytest -q` в venv и предоставь реальный вывод. Убедись, что `start.py` стартует без неявных облачных запросов кроме первичной загрузки модели. Просмотри код, исправь настоящие ошибки, добавь version/health diagnostics.
2. Не ломай существующую лампу, Ollama и 9 тестов. Не добавляй медленные модели по умолчанию без выбора/бенчмарка.
3. Добавь единый конфиг и экран проверки инфраструктуры: Ollama reachable? model installed? STT loaded? GPU/CPU? TTS installed? Без токенов в ответе.
4. Commit `baseline-good` и отчёт `docs/STATUS.md` с проверенными фактами.

### M1 — Русская речь: не гадать, а тестировать

1. Профили STT: **Fast/CPU**, **Balanced**, **Quality/GPU**. Сравнить `base`, `small`, `medium` либо другой совместимый multilingual model на тех же 25–40 русских фразах; не подсовывать English-only или distil-English как основную RU-модель.
2. Отделить захват WebM → декодирование → VAD → распознавание. Вставить VAD, настройку `language=ru`, `beam_size`, таймауты, варианты `hotwords`/`initial_prompt` для названий приложений. Экспериментально проверить, не ухудшает ли hotwords общую речь. Задокументировать значения и причины.
3. Проверять вход: длительность, пустая запись, формат, HTTP размер, отсутствие речи. Не устранять ошибку слепой заменой произнесённого текста; показать сырой transcript и дать **исправить текст до исполнения** на UI. При низкой уверенности/неоднозначности/похожих именах уточнять.
4. Обработчик длинных формулировок, отрицаний и вопросов должен различать «открой» и «как открыть» без выполнения.
5. До любых заявлений о качестве запустить записанные самим пользователем тесты. Сделать `scripts/eval_stt.py` (референс CSV + каталог записей, подсчет WER/CER), сохранять анонимные метрики, а **записи только по явному opt-in**.

### M2 — Умный и безопасный каталог приложений Windows (ключевая фича)

1. Динамически перечислять программы из Start Menu shortcuts (`%APPDATA%`, `%ProgramData%`), Desktop, подходящих Windows App Paths/проверенных установленных приложений, поддерживаемых UWP/MSIX по возможности. Не ограничиваться двумя именами. Отображать каталог в UI и API.
2. Поддержать псевдонимы и русские названия («блокнот» ↔ Notepad, «кодекс» ↔ Codex, «vs code» ↔ Visual Studio Code, «дискорд» ↔ Discord). Не выдумывать установленность: `open Codex` — запуск только если реальный путь/регистрация существуют, иначе понятное сообщение и выбор из установленных вариантов. Если «Codex» — плагин/CLI, не подменять его произвольным терминалом или VS Code без согласия.
3. Алгоритм: STT/text → intent (action/info) → идентификация целевого приложения в **наблюдаемом каталоге** → проверка уверенности/политики → безопасный OS launcher → status. LLM может выбрать ID из каталога, но **не может** подать raw shell command, URL, cwd, path or process name.
4. Использовать абсолютный проверенный путь/специальный проверенный механизм Windows (например зарегистрированное приложение), `shell=False`, безопасные аргументы; реестр и .lnk считать источником метаданных, ссылку резолвить с проверкой. Не запускать исполняемые цели из временных/untrusted сетевых папок без отдельного разрешения. Не делать wildcard запуск процессов.
5. «Закрой» — максимум корректно и по возможности мягко закрыть окно/экземпляр, который запустил LocalMind, без потери данных. Никогда не `taskkill /IM ... /F` по умолчанию. Если безопасно нельзя — объяснить, почему, предложить открыть менеджер окон без автоматического закрытия.
6. Менеджер подключаемых действий и user-managed app aliases; ask once для нового действия. Audit log: requested name, resolved app id, granted?, success/fail, duration. Не сохранять секреты и голос.
7. Отдельные тесты на отрицание, омонимы, malicious shortcut, subcommand injection, неразрешённую Windows команду, `cmd`, `powershell`, путь с `&`, имена файлов похожие на программы, длинный LLM output, ambiguous app.

### M3 — Корректный агент, локальная озвучка, состояние разговора

1. Вопросы по знаниям (RSA, рецепты, школьные темы) обрабатывать как разговор без списка инструментов. Действия только при **явном** намерении. Не уверены — безопасно уточнить.
2. Предпочитать структурированный ответ и контроль аргументов на сервере (JSON schema / tool calling). Строго ограничить количество tool calls и время. Действие считается успешным только после ответа адаптера.
3. Полноценный **локальный TTS** (Piper или доказанный аналог) с поддержкой русского, голосовой ответ и переключатель mute; раздельная телеметрия STT, route, LLM, action, TTS (p50/p95).
4. Push-to-talk сначала; **не включать непрерывный фоновой микрофон без явного opt-in**. UI: запись → STT → редактирование текста → подтверждение действия (если требуется) → ответ → воспроизведение. Если обычный вопрос, можно отправлять автоматически по явной настройке.
5. Офлайн демонстрация после разовой загрузки моделей. Обрабатывать отсутствие интернета, ошибки, зацикливание, пустое распознавание, медленные ответы и рассинхронизацию UI.

### M4 — Интерфейс, безопасные интеграции, качество

1. Современный быстрый адаптивный тёмный интерфейс: чат, большая кнопка микрофона, видимый transcript (исходный и вручную исправленный), приложение/обнаружение, permission dialogs, состояние Ollama/GPU, voice settings, устройства (явно DEMO/REAL), внятные ошибки и времена задержек. UI на русском, читабельный с 100%/125%/140% масштабом браузера.
2. Home Assistant сохраняется через безопасный adapter. Не заявлять «поддерживаем любые устройства AliExpress»; только подключённые и разрешённые сущности. Действия на устройствах подтверждены ответом сервиса; обновить actual state через HA, если реально возможно.
3. Локальный клиент «колонка» как отдельное приложение/сателлит только ПОСЛЕ того, как localhost голос работает стабильно; не использовать небезопасный открытый HTTP LAN с микрофоном/ключом. Если нет времени — качественная демонстрация с телефона/ноутбука/без железа лучше нерабочего ESP32.
4. Не портить Windows/Windows Firewall; никаких установщиков драйверов и включения портов без понятных запросов.

### M5 — Документация, исследования, готовность к защите

1. Повторяемые эксперименты: 30+ записанных коротких RU команд в нескольких условиях (тихо, фоновый шум, разные длины), WER/CER, success rate разрешения приложений и end-to-end, p50/p95 задержки. Без файла записи / реальной Windows тестовой машины — НЕ писать выдуманных процентов.
2. Провести security tests, UX smoke test, test matrix (good/negative/ambiguous). Каждая фича должна иметь доказательство, репродуцируемый скрипт либо явно указанный ручной шаг.
3. Финальные файлы: `README.md`, `docs/ARCHITECTURE.md`, `docs/HOW_IT_WORKS.md`, `docs/DEFENSE_QA.md` (30+ вопросов; STT, VAD, LLM, tools, shortcut/registry, security, RTX 4070, privacy, latency, Home Assistant), `docs/EXPERIMENTS.md` (измерения), `docs/KNOWN_LIMITATIONS.md`, `docs/CHANGELOG.md`, `docs/STATUS.md`.
4. Комплект для конференции 10–11 классов: корректная проблема, цель, гипотеза/техническая задача, собственный вклад, сравнение с существующими системами, эксперимент, воспроизводимость. Не писать за пользователя несуществующие отзывы/опыты.
5. Речь для двух авторов: техническая часть у разработчика; выступление, сценарий демонстрации, методика испытаний и вопросы про применение у второго участника — при условии его реального вклада.

## 3. Definition of Done (без косметики)

- Поставляется clean Git repo с единой командой запуска, документированными версиями, понятными профилями STT/TTS.
- После установки и загрузки моделей полностью локальный RU speech → knowledge answer → RU TTS работает на localhost.
- Минимум **5 обнаруженных реальных приложений Windows**, если они установлены; запуск из каталога и отказ от небезопасного target. В числе тестовых фраз — «Открой Codex», но отсутствие установленного Codex нельзя выдавать за сбой или успешный запуск.
- Все 9 старых тестов, новые unit/integration/security tests зелёные. Windows-only tests при недоступной Windows помечены NOT TESTED.
- UI показывает raw STT, позволяет правку, показывает что реально было сделано, а не текст-галлюцинацию LLM.
- DEMO переключение лампы и обычные вопросы не регрессировали; реальные HA команды ТОЛЬКО при наличии HA, конфигурации и согласия.
- Не изобретено ни одного неподтверждённого результата замера/тестирования. Нет произвольного исполнения команд или убийства процессов.
- Полные объяснения важных технических решений в docs, автор способен рассказать об архитектуре без DevCrew.

## 4. Рабочая дисциплина DevCrew

- **Architect** анализирует проблемы, интерфейсы, план, риски, бюджет VRAM. До кода обновляет `docs/DECISIONS.md`.
- **Builder** делает небольшие проверяемые реализации.
- **Tester** пишет позитивные, негативные, компонентные и регрессионные тесты, воспроизводит баги из `docs/USER_FAILURES.md`.
- **Reviewer** проверяет архитектурные решения, пользовательские сценарии и соблюдение границ.
- **Security** атакует parser/executor и проверяет отсутствие скрытого исполнения команд или утечек в LAN.
- **Visual QA** проверяет состояния интерфейса со скринами, если браузер доступен; иначе чётко сообщает, что не проверял.
- В конце каждой milestone: git commit, `docs/STATUS.md` факты, тест logs, next step. При блокере — не маскировать, сохранять рабочий код и продвигаться к следующей независимой безопасной задаче.

Время или объём токенов сами по себе не критерий успешности. Результат — работающий проверенный продукт.
